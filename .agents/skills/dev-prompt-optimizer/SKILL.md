# Dev Prompt Optimizer

지저분한 개발 의도를 코딩 LLM이 신뢰성 있게 실행할 수 있는 프롬프트로 변환한다.

다음 경우에 이 스킬을 사용한다:
- 기능, 버그, 리팩토링, 코드 변경을 느슨한 자연어로 설명하는 경우
- 모델이 의도를 잘못 이해했다고 말하는 경우
- 더 나은 구현 품질을 얻기 위해 프롬프트를 재작성하고 싶은 경우
- 요구사항이 불완전하거나 제약 조건이 빠져있거나 성공 기준이 불명확한 경우
- Codex, Claude Code, ChatGPT, Cursor 등 다른 코딩 LLM을 위한 프롬프트가 필요한 경우

다음 경우에는 이 스킬을 사용하지 않는다:
- 사용자가 이미 정밀하고 실행 가능한 프롬프트를 제공한 경우
- 사용자가 프롬프트 최적화가 아닌 코드 즉시 작성을 원하는 경우
- 개발 요청이 아닌 단순 사실 질문인 경우

## 목표

출력은 코딩 모델의 성능을 저하시키는 실패 요인을 줄여야 한다:
- 모호한 작업 경계
- 저장소 또는 파일 맥락 누락
- 불명확한 성공 기준
- 숨겨진 제약 조건
- "반드시 해야 할 것"과 "있으면 좋은 것" 혼재
- 검증 또는 테스트 기대치 없음
- 관련 없는 코드를 리팩토링할 암묵적 허가

## 언어 규칙

**모든 출력은 반드시 한국어로 작성한다.** 진단, 세그먼트 리뷰, 질문 목록, 최종 프롬프트를 포함한 모든 섹션을 한국어로 출력한다. 사용자가 영어로 입력해도 출력은 한국어를 사용한다.

## 운영 규칙

개발 작업을 직접 해결하지 않는다. 더 나은 프롬프트로 재작성만 한다.

사용자가 최적화와 실행 모두를 요청하면, 먼저 최적화된 프롬프트를 생성한 후 실행 작업을 명확히 분리하여 진행한다.

## 워크플로우

재작성 전에 아래 루브릭으로 입력 프롬프트를 먼저 점수화한다.

### 0단계. 전수 의도 확인 (항상 실행)

최적화 전에 반드시 이 단계를 실행한다. 단계를 건너뛰지 않는다.

입력 프롬프트에서 언급된 모든 사항을 빠짐없이 리스트업한다. 명확해 보이는 항목도 제외하지 않는다.

리스트업 기준:
- 요청된 기능 / 변경사항 / 목표
- 언급된 파일, 모듈, 기술 스택, 환경
- 제약 조건 또는 하지 말아야 할 것
- 성공 기준 또는 완료 조건
- 테스트 / 검증 방법
- 스타일, 아키텍처, 형식에 대한 선호
- 암묵적으로 전제된 맥락

리스트업이 완료되면, **모든 항목에 대해 질문**한다:
- 명확해 보이는 항목: "이 의도가 맞는지" 확인 질문
- 불명확한 항목: 확정될 수 있도록 구체적인 선택지 또는 설명 요청
- 누락된 항목: 실행에 필요한 정보를 요청

질문 형식:
```
## 의도 확인 질문

다음 항목을 모두 확인한 후 최적화된 프롬프트를 작성합니다.
답변해 주시면 반영하겠습니다.

### [항목 번호]. [항목명]
- 현재 이해: [프롬프트에서 파악한 내용]
- 질문: [확인 또는 명확화 요청]
```

사용자가 모든 질문에 답변한 후에만 다음 단계로 진행한다.
사용자가 "바로 최적화해줘" 또는 "질문 없이 진행해줘"라고 명시한 경우에만 이 단계를 건너뛴다.

### 1단계. 의도 추출

사용자의 거친 언어에서 실제 작업을 추론한다:
- 원하는 변경 사항
- 왜 중요한지
- 어디에 적용될 가능성이 높은지
- 어떤 종류의 출력이 기대되는지

추가 범위를 임의로 만들기보다 사용자 의도를 보존하는 것을 우선한다.

### 2단계. 프롬프트 세그먼트 분리

입력 프롬프트가 길면 품질 판단 전에 의미 있는 블록으로 분리한다.

문장 경계가 아닌 의도 기준으로 분리한다. 일반적인 블록 유형:
- `작업(Task)` - 무엇을 할지
- `목표(Goal)` - 성공이 무엇을 달성해야 하는지
- `맥락(Context)` - 저장소, 제품, 버그, 이전 동작, 파일, 스택
- `제약(Constraint)` - 제한, 제외, 안전 장치
- `검증(Validation)` - 테스트, 재현, 확인
- `선호(Preference)` - 스타일 또는 소프트 선호
- `노이즈(Noise)` - 군더더기, 반복, 감정, 추측

각 블록은 다음 리뷰 판정 중 하나를 받아야 한다:
- `유지(KEEP)` - 강력하고 직접적으로 유용함
- `재작성(REWRITE)` - 유용한 아이디어지만 표현이 약함
- `명확화(CLARIFY)` - 중요하지만 불충분하게 명시됨
- `제거(REMOVE)` - 실행에 유용하지 않음

### 3단계. 모호성 정규화

모호한 언어를 명시적인 작업 구조로 변환한다:
- "더 좋게 해줘"를 likely 품질 목표로 대체
- 버그 증상과 근본 원인 추측을 분리
- 필수 동작과 선호 사항을 분리
- 암묵적 제약을 직접적인 지침으로 변환

세부 사항이 빠져있지만 안전한 가정이 가능하면 가정임을 표시하여 유지한다.
빠진 세부 사항이 차단적이거나 고위험이면 짧은 명확화 섹션으로 표면화한다.

### 4단계. 실행 가드레일 추가

다음을 명시하여 프롬프트를 더 안전하고 신뢰성 있게 만든다:
- 알려진 경우 대상 파일, 모듈, 영역
- 알려진 경우 기술 또는 런타임
- 범위 제약 조건
- 변경하지 말아야 할 것
- 필요한 테스트 또는 검증
- 기대되는 최종 결과물

### 5단계. 신호 강화, 노이즈 제거

실행에 도움이 되지 않는 군더더기, 반복, 감정적 표현, 추측적 추론을 삭제한다.

유지할 것:
- 구체적인 사실
- 제약 조건
- 의도를 명확히 하는 예시
- 인수 기준

### 6단계. 최적화된 프롬프트 생성

다른 코딩 LLM이 직접 실행할 수 있는 프롬프트를 반환한다.

## 점수 루브릭

최적화 전에 원본 입력을 점수화한다. 실행 간 평가의 일관성을 유지하기 위해 100점 척도를 사용한다.

| 카테고리 | 가중치 | 측정 기준 |
| --- | --- | --- |
| 의도 명확성 | 20 | 요청된 결과가 명시적이고 재서술하기 쉬운가? |
| 범위 정의 | 15 | 프롬프트가 범위 내/외를 명시하는가? |
| 맥락 완성도 | 15 | 관련 저장소, 기능, 버그, 스택, 파일 맥락이 포함되어 있는가? |
| 제약 및 가드레일 | 15 | 비협상 사항, 제한, "변경 금지" 규칙이 명시적인가? |
| 성공 기준 | 15 | 모델이 "완료"가 어떤 모습인지 알 수 있는가? |
| 검증 가이드 | 10 | 테스트, 확인, 재현 단계가 제공되는가? |
| 신호 대 노이즈 비율 | 10 | 프롬프트가 주로 실행 가능한 정보로 구성되어 있는가? |

총점 = 100.

### 카테고리 점수 가이드

각 카테고리에 이 5단계 척도를 사용한다:

| 점수 구간 | 의미 |
| --- | --- |
| 카테고리 가중치의 0-20% | 없거나 거의 사용 불가 |
| 21-40% | 약함, 높은 모호성 |
| 41-60% | 부분적, 사용 가능하지만 위험 |
| 61-80% | 좋음, 적당한 gaps만 있음 |
| 81-100% | 강함, 명확하고 실행 준비 완료 |

예시:
- 가중치 `15`인 카테고리는 `0-3`, `4-6`, `7-9`, `10-12`, `13-15`로 점수화
- 가중치 `10`인 카테고리는 `0-2`, `3-4`, `5-6`, `7-8`, `9-10`으로 점수화

## 등급 구간

총점을 판정 구간으로 변환한다:

| 총점 | 등급 | 사용 판정 |
| --- | --- | --- |
| 90-100 | A | 바로 사용 가능 |
| 75-89 | B | 사용 가능하나 최적화 권장 |
| 60-74 | C | 위험, 사용 전 최적화 필요 |
| 40-59 | D | 오작동 가능성 높음, 재작성 필요 |
| 0-39 | F | 실행 불가 |

## 평가 출력

항상 재작성된 프롬프트 전에 진단을 포함한다.
항상 결과를 복사 가능한 Markdown으로 반환한다.

## 선호 출력 형식

사용자가 다른 Markdown 형식을 요청하지 않으면 아래 구조를 사용한다. 모든 텍스트는 한국어로 작성한다.

```markdown
## 의도 확인 질문

다음 항목을 모두 확인한 후 최적화된 프롬프트를 작성합니다.
답변해 주시면 반영하겠습니다.

### 1. [항목명]
- 현재 이해: [프롬프트에서 파악한 내용]
- 질문: [확인 또는 명확화 요청]

### 2. [항목명]
...

---
(사용자 답변 후 아래 섹션 작성)
---

## 프롬프트 진단
- 의도 명확성: [점수]/20
- 범위 정의: [점수]/15
- 맥락 완성도: [점수]/15
- 제약 및 가드레일: [점수]/15
- 성공 기준: [점수]/15
- 검증 가이드: [점수]/10
- 신호 대 노이즈 비율: [점수]/10

## 총점
[점수]/100

## 등급
[A-F]

## 사용 판정
[바로 사용 가능 | 최적화 권장 | 최적화 필요 | 재작성 필요 | 실행 불가]

## 세그먼트 리뷰
1. [인용 또는 요약된 블록]
- 유형: [작업 | 목표 | 맥락 | 제약 | 검증 | 선호 | 노이즈]
- 판정: [유지 | 재작성 | 명확화 | 제거]
- 이유: [설명]

## 강점
- [실행에 도움이 되는 부분]

## 실패 위험
- [잘못 해석될 가능성이 있는 부분]

## 누락 정보
- [실행에 실질적으로 영향을 주는 누락 항목만]

## 작업
[한 문장으로 표현한 작업]

## 목표
[성공 시 결과]

## 맥락
- [저장소, 기능, 버그, 사용자 의도, 알려진 사실]

## 제약 조건
- [범위 제한]
- [기술 제약]
- [스타일 또는 아키텍처 제약]

## 해야 할 것
- [필수 작업]

## 하지 말아야 할 것
- [모델이 반드시 피해야 할 것]

## 완료 기준
- [관찰 가능한 완료 조건]

## 검증
- [테스트, 확인, 수동 검증 방법]

## 미결 질문
- [정말 차단적이거나 위험한 경우에만]

## 최종 프롬프트
[다른 LLM에 바로 붙여넣을 수 있는 완성된 프롬프트]
```

## Markdown 출력 규칙

전체 결과는 사용자가 직접 복사할 수 있는 Markdown으로 반환한다.

- Markdown 헤딩과 플랫 불릿 사용
- 실행 간 구조 안정성 유지
- 사용자가 명시적으로 요청하지 않는 한 전체 답변을 코드 블록으로 감싸지 않음
- 사용자가 완전히 복사 가능한 결과물을 원하면 `최종 프롬프트`를 `text` 코드 블록 안에 유지
- 사용자가 "복사 가능 md", "마크다운", "md"를 명시적으로 요청하면 구조 외부에 추가 주석 없이 깔끔한 Markdown으로 전체 결과를 반환

## 프롬프트 작성 규칙

`최종 프롬프트`는 다음을 따른다:
- 긴 서문이 아닌 작업으로 시작
- 구현 세부 사항 전에 원하는 결과를 명시
- 가능한 경우 저장소 또는 파일 맥락 포함
- 제약 조건을 명시적으로 서술
- 최소한의 관련 변경 요청
- 검증 단계 요청
- 유용한 경우 기대되는 응답 형식 정의

`최종 프롬프트`는 다음을 피한다:
- 정의 없이 "보기 좋게 해줘" 같은 모호한 표현
- 사용자가 요청하지 않은 광범위한 리팩토링 요구
- 관련 없는 아키텍처 변경을 모델이 선택하도록 허용
- 사용자가 명시적으로 번들링을 원하지 않는 한 여러 독립 작업 혼합
- 제공된 적 없는 숨겨진 맥락 가정

## 가정 정책

가정이 필요한 경우 다음 두 가지 모드 중 하나를 사용한다:

- **안전한 가정**: 간단한 `가정` 메모를 포함하고 계속 진행
- **차단적 모호성**: 강력한 초안 프롬프트를 만들 수 없을 때만 `미결 질문`에 최소한의 질문 포함

강력한 초안 프롬프트를 만들 수 있다면 탐색 질문으로 사용자를 압도하지 않는다.

거친 언어를 더 날카로운 지침으로 재작성한다:

| 약한 표현 | 더 강한 개발 프롬프트 표현 |
| --- | --- |
| "이 이상한 문제 고쳐줘" | "근본 원인을 파악하고 타겟팅된 수정을 구현한다" |
| "더 깔끔하게 해줘" | "외부 동작을 변경하지 않고 가독성을 향상한다" |

## 출력 품질 기준

강력한 결과:
- 원본 요청보다 작업 실행을 더 쉽게 만든다
- 해석 오차를 줄인다
- 방대해지지 않고 행동하기에 충분한 세부 사항을 제공한다
- 성공 기준에 대한 의심을 남기지 않는다

약한 결과:
- 단순히 다시 표현한 것
- 동일한 모호성 유지
- 실행 가능한 구조 대신 일반적인 군더더기 추가

## 일관성 규칙

평가를 안정적으로 유지하기 위해:
- 최적화 전에 원본 프롬프트를 먼저 점수화
- 긴 프롬프트는 약점을 점수화하기 전에 세그먼트 분리
- 모든 것을 재작성하는 대신 강력한 블록 보존
- 의도가 친숙하게 느껴진다고 점수를 부풀리지 않음
- 구현이 쉬워 보여도 검증 누락에 감점
- 기능 요청이 합리적으로 들려도 불명확한 범위에 감점
- 인접한 두 점수가 가능해 보이면 명시적인 증거가 없는 한 낮은 점수 선택
- 이전 턴의 숨겨진 가정이 아닌 프롬프트가 말하는 것에 기반하여 점수화

```
## 의도 확인 질문

다음 항목을 모두 확인한 후 최적화된 프롬프트를 작성합니다.
답변해 주시면 반영하겠습니다.

### 1. 개선 대상 페이지
- 현재 이해: 설정 페이지(settings page)를 수정한다
- 질문: 어떤 파일 또는 컴포넌트가 설정 페이지인지 알고 있으신가요? (예: SettingsPage.tsx, /settings 라우트 등)

### 2. "지저분하다"는 표현
- 현재 이해: 레이아웃이나 UI가 정돈되지 않은 상태
- 질문: "지저분하다"는 것이 레이아웃 구조 문제인지, 시각적 스타일 문제인지, 아니면 저장 버튼 위치만의 문제인지 어느 쪽인가요?

### 3. 저장 버튼을 놓치는 문제
- 현재 이해: 저장 버튼이 눈에 잘 띄지 않아 사용자가 찾지 못함
- 질문: 버튼의 위치가 문제인가요, 스타일(색상, 크기)이 문제인가요, 아니면 둘 다인가요?

### 4. "너무 많이 바꾸지 않는다"는 제약
- 현재 이해: 최소한의 변경만 허용
- 질문: 변경 허용 범위가 어느 정도인가요? (예: 버튼 스타일만, 버튼 위치 이동 가능, 섹션 구조 변경 불가 등)

### 5. 기술 스택 / 디자인 시스템
- 현재 이해: 명시되지 않음
- 질문: 사용 중인 UI 라이브러리나 디자인 시스템이 있나요? (예: MUI, Tailwind, shadcn/ui 등)

### 6. 성공 기준
- 현재 이해: 저장 버튼이 더 눈에 띄면 완료
- 질문: "더 눈에 띄게"의 기준을 어떻게 판단하실 건가요? (예: 특정 위치에 고정, 특정 색상 사용, 사용자 테스트 등)

### 7. 검증 방법
- 현재 이해: 명시되지 않음
- 질문: 변경 후 어떻게 검증할 계획인가요? (예: 스냅샷 테스트, 수동 확인, 반응형 확인 등)
```
